Your AI Agent Needs a Job Description and a Locked Door

7 September 2026

AI assistants are becoming AI agents. The difference matters. An assistant suggests what to do. An agent may open files, call software, send messages, update records or make changes while nobody is watching every step.

That can save time. It can also turn a vague instruction, excessive permission or malicious content into a real business action.

The National Cyber Security Centre has now published practical advice for organisations deploying agentic AI. Its central message is straightforward: the more autonomy an agent has, the greater the consequences when it behaves unexpectedly, reaches information it should not see or acts outside its intended scope.

For UK SMEs, this is not a reason to avoid AI. It is a reason to stop treating an AI agent like an ordinary software subscription.

The Risk Is What the Agent Can Do

An AI agent does not need to be malicious to cause harm. It may follow a badly defined objective, misunderstand context or act on instructions hidden inside a document, website or email.

The practical risk depends on its access. An agent connected only to a folder of approved marketing material has a limited impact. An agent that can read every mailbox, access customer records, issue refunds, change cloud settings or publish externally has a much larger blast radius.

Start with permissions, not promises. Ask what the agent can read, what it can change, which credentials it can use and whether it can communicate outside the business.

Give Every Agent a Written Job

Before connecting an agent to business systems, write down its purpose in plain English. Define the tasks it may perform, the data it may use, the actions it must never take and the moments when a person must approve the next step.

This is more than a prompt. It is an operating boundary. A useful definition should answer:

  • What outcome is the agent allowed to pursue?
  • Which systems and data does it genuinely need?
  • Which actions require approval before they happen?
  • What must make the agent stop?
  • Who owns the agent and reviews its activity?

If nobody can answer those questions, the agent is not ready for production access.

Use a Separate Identity

Do not let an agent operate through a director's account or a shared administrator login. Give it a unique identity with only the permissions required for its specific task.

Short-lived credentials are preferable to permanent keys. Remove access when a trial ends. Keep production data away from experiments. Where possible, use a controlled service to supply credentials without revealing the secret directly to the agent.

This makes activity easier to attribute and limits the damage if the agent, its instructions or a connected service is compromised.

Put Approval Gates Around Consequential Actions

Some actions should never happen just because an agent decided they were useful. Sending external email, changing bank details, deleting records, publishing content, creating users and altering security settings should normally require explicit human approval.

The approval needs to be technically enforced. Telling an agent to ask first is not the same as preventing it from acting without permission.

For lower-risk work, a person may monitor activity and intervene when needed. For higher-risk work, require approval before the action. If the business could lose money, expose personal information or interrupt operations, do not rely on retrospective review.

Restrict the Environment

The NCSC recommends running agents in a robust sandbox. For an SME, the principle is simple: an agent should not be able to wander across the network, local computer or cloud estate.

Allow only the destinations and tools required for the job. Separate test and production environments. Restrict outbound network access. Do not leave unrelated API keys, browser sessions, shared drives or administrator credentials within reach.

A sandbox is not one setting. It includes the computer the agent runs on, the network it can reach, the credentials it can use and the information it can read.

Keep Logs You Can Trust

An agent's activity should be treated like user activity. Record what it accessed, which tools it called, what changes it made and which approvals it received.

Protect those logs from alteration and review them. Begin new deployments during working hours, when someone is available to investigate unexpected behaviour. Expand autonomy only after the controls have been tested in practice.

If the only record is the agent's own summary of what it did, the business does not have reliable oversight.

Make the Off Switch Real

Every agent needs a tested shutdown process. Stopping the visible task may not be enough. The business may also need to revoke credentials, block network access, disable integrations and prevent queued actions from continuing.

Write down who can stop the service and how. Test that process before the agent handles sensitive information or consequential actions.

Questions to Ask Before the Next AI Integration

  • What systems, data and credentials can the agent reach?
  • Does it have its own identity and minimum permissions?
  • Which actions are blocked until a person approves them?
  • Can untrusted emails, websites or documents influence its instructions?
  • Where does it run, and what prevents it reaching unrelated systems?
  • What activity is logged, and who reviews those logs?
  • Can we stop it immediately and revoke every connection?
  • Who remains accountable when the agent makes a mistake?

The bigredbox Take

An AI agent should be treated as a fast, capable but untrusted operator. Give it a narrow job, a separate identity, limited access, reliable supervision and a real off switch.

The goal is not to remove every risk before using AI. It is to make sure one unexpected decision cannot become an email sent to every customer, a deleted dataset, an unauthorised payment or an exposed network.

Start with a small task. Keep the agent away from production. Add access only when the business can see, approve and reverse what it does.

Autonomy is a permission, not a feature to enable by default.
