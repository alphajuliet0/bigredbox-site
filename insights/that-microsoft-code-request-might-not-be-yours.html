That Microsoft Code Request Might Not Be Yours

29 June 2026

Most phishing training still tells staff to look for a fake login page. That advice is useful, but it is no longer enough. Some attacks now send people to a genuine Microsoft sign-in page and ask them to enter a device code. The page is real. The login flow is real. The problem is that the request was started by the attacker.

This is known as device-code phishing. It matters for UK SMEs because Microsoft 365 is often the centre of the business: email, files, Teams, finance conversations, customer records and supplier approvals all depend on it.

If an attacker gets a valid session, they may not need your password again. They can read mail, create forwarding rules, search files, impersonate staff and prepare invoice fraud.

How the Attack Works

Device-code sign-in exists for legitimate reasons. It helps devices with limited keyboards or screens sign in by showing a short code that the user enters on another device. Used properly, it is convenient.

In a phishing attack, the criminal starts the sign-in on their own system and sends the victim the code. The victim is told to open the Microsoft device login page and enter it. If the user signs in and approves the request, the attacker receives access to the account or app session.

The user may believe they have completed a normal security check. In reality, they have authorised someone else's sign-in.

Why This Beats Old Phishing Advice

There may be no obviously fake website. The address may be a genuine Microsoft address. Multi-factor authentication may still appear. That is why staff awareness needs to move from simple URL checking to context checking.

The key question is not only, Is this a real Microsoft page? It is also, Did I start this sign-in?

If the answer is no, the code should not be entered.

What Staff Need to Know

Keep the user rule simple:

  • Do not enter a Microsoft device code unless you personally started the sign-in.
  • Do not approve a sign-in request because an email, Teams message or phone call tells you to.
  • Stop and report any unexpected code, approval prompt or re-authentication request.
  • If you entered a code and feel unsure, report it immediately. Early reporting can prevent damage.

This is not about blaming staff. A realistic-looking sign-in flow is designed to feel safe. The business needs a process that makes reporting quick and normal.

What Admins Should Check

For Microsoft 365 environments, the practical work sits in identity controls and sign-in visibility.

Review Device-Code Sign-In

Not every business needs device-code authentication enabled broadly. Review whether it is required, which users or apps need it and whether Conditional Access can restrict or block authentication flows that introduce unnecessary risk.

Watch for Unusual Sign-Ins

Look for sign-ins from unusual locations, unfamiliar devices, unexpected applications and device-code authentication events. If your licence level allows it, use sign-in logs and risk-based alerts. If you work through an IT provider, ask them what they monitor and how quickly they will tell you.

Protect High-Value Accounts First

Directors, finance users, mailbox administrators and anyone who can reset passwords or approve payments should have the strongest controls. Shared administrator accounts should be removed. Privileged access should be separated from everyday email use.

Reduce Standing Access

If a third-party app or old integration no longer needs access, remove it. Attackers often look for tokens, app permissions and forgotten connections that give them a quieter route into data.

How to Respond If Someone Entered a Code

Speed matters. Treat it as a possible account compromise, not as a training issue.

  1. Reset the user's password and revoke active sessions.
  2. Check sign-in logs for unfamiliar locations, devices and applications.
  3. Review mailbox forwarding rules, inbox rules and delegated access.
  4. Check files, Teams chats and recent downloads for sensitive data exposure.
  5. Look for payment, invoice or supplier conversations that may have been accessed.
  6. Inform your IT provider, insurer or incident support contact if the account is high risk.

Do not wait for clear evidence of fraud before taking containment steps. A few minutes can make the difference between an awkward reset and a wider business email compromise incident.

Questions to Ask Your IT Provider

  • Is device-code authentication currently allowed in our Microsoft tenant?
  • Can we restrict it to only the users or apps that genuinely need it?
  • Do we monitor device-code sign-ins?
  • Who receives alerts for unusual sign-in behaviour?
  • How quickly can we revoke sessions if an account is compromised?
  • When did we last review third-party app permissions?

If these questions cannot be answered clearly, write them down as actions. Identity security is now a business control, not just an IT setting.

The bigredbox Take

Device-code phishing works because it borrows trust from a legitimate login process. That makes it a good example of where cyber security has moved: the page can be real and the request can still be malicious.

For SMEs, the fix is not complicated. Teach staff to ask whether they started the sign-in, restrict risky authentication flows where possible, monitor sign-in behaviour and rehearse fast account containment.

If Microsoft 365 runs your business, sign-in control is business continuity.
