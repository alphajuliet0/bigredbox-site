Your Software Has a Family Tree, and Attackers Know It

8 June 2026

Your business probably uses far more software than appears on its asset list. A website plugin may depend on dozens of libraries. A CRM integration may pull in code maintained by people you have never heard of. A developer may install a trusted package that quietly brings another hundred components with it.

That is how modern software is built. It is fast, efficient and usually sensible. It also creates a family tree of dependencies that attackers are learning to exploit.

On 4 June 2026, the National Cyber Security Centre warned that attackers are compromising open source packages at scale to spread malware through trusted software ecosystems. The warning followed recent attacks against package managers and developer tools, including the May 2026 Mini Shai-hulud campaign.

This may sound like a developer problem. It is a business problem.

Why UK SMEs Should Care

Most SMEs do not build large software platforms, but they depend on organisations that do. Your website agency, managed IT provider, app developer, e-commerce platform and SaaS suppliers all use third-party components. If one trusted dependency is compromised, malicious code can travel downstream into many customers before anyone notices.

The damage can include stolen API keys, exposed customer data, compromised cloud accounts, payment redirection and malware appearing inside a legitimate update. The initial weakness may sit several suppliers away, but the operational and regulatory consequences still arrive at your business.

The central issue is visibility. You cannot manage a dependency nobody knows exists.

What Attackers Are Exploiting

Open source software is not inherently unsafe. The risk comes from the combination of scale, automation and trust.

  • Compromised maintainer accounts. Attackers steal credentials or access tokens, then publish a malicious update under a trusted name.
  • Abandoned packages. A package that is no longer actively maintained may be taken over or left with known vulnerabilities.
  • Typosquatting. A malicious package is given a name that looks almost identical to a legitimate one, hoping a developer installs it by mistake.
  • Automatic propagation. Build systems can download and run updated packages without a person reviewing the change.
  • Stolen developer secrets. API keys, signing credentials and registry tokens stored on developer devices can provide access to other systems.

Questions to Ask Your Developer or IT Provider

You do not need to become a software engineer. You do need clear answers from the people who build and maintain your systems.

  • Do we have an inventory of the third-party packages and components used in our website, applications and integrations?
  • How are new dependencies approved?
  • Are package updates installed automatically, or are they reviewed and tested first?
  • Do you scan dependencies for known vulnerabilities and malicious packages?
  • Are developer, source-code and package-registry accounts protected by multi-factor authentication?
  • Where are API keys, tokens and deployment credentials stored?
  • How quickly could you identify whether we use a package named in a security alert?
  • Would you notify us if a dependency compromise affected our service?

If a supplier cannot answer these questions, the problem is not that you asked something too technical. The problem is that they may not have sufficient control of the software they provide.

Practical Controls for SMEs

  • Keep a software dependency inventory. For custom software, ask for a software bill of materials or another maintained list of components and versions.
  • Reduce unnecessary plugins and integrations. Every component adds maintenance work and another potential route into the system.
  • Review updates before production. Security patches should move quickly, but blindly accepting every new dependency version creates a different risk.
  • Use controlled build and deployment processes. Production releases should not depend on one developer laptop or personal account.
  • Protect developer identities. Require MFA for source-code platforms, package registries, hosting control panels and cloud services.
  • Keep secrets out of source code. API keys and passwords should be stored securely, limited in scope and rotated after suspected exposure.
  • Set supplier expectations in writing. Contracts should cover vulnerability management, incident notification, access control and support for end-of-life components.

If You Suspect a Compromised Dependency

Pause affected deployments, preserve logs and identify where the component is used. Review recent version changes, unusual network traffic and unexpected use of developer credentials. Rotate exposed tokens and API keys rather than assuming a password change is enough.

Do not delete evidence in the rush to recover. A clean rebuild from trusted components may be required, but first establish what changed, what had access and which downstream systems may be affected.

The bigredbox View

Software supply-chain security is often discussed as if it belongs only to large technology companies. In reality, smaller businesses are heavily exposed because they rely on external developers, plugins, SaaS services and automated integrations while having limited visibility into how those products are assembled.

The answer is not to reject open source software or stop updating systems. It is to know what you depend on, control how changes enter production and make suppliers accountable for the components they choose.

Your business does not need to understand every line of code. It does need to know who is responsible when trusted code turns hostile.
